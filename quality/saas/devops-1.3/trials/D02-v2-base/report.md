# Decision: revise; acceptance blocked on verification

The original design fails two state requirements and the connection-boundary assumption. KV reads are eventually consistent, with changes potentially delayed 60 seconds or more; KV is unsuitable for atomic read/write transactions. Serializing KV writes through Durable Objects would still leave stale KV reads. Durable Objects offer transactional, strongly consistent storage within an object, but this proposal instead uses one PostgreSQL primary for authorization and inventory. [Cloudflare KV](https://developers.cloudflare.com/kv/concepts/how-kv-works/), [Durable Objects](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/).

Cloud Run can briefly exceed its configured maximum. Treat scaling as cost/capacity control, never the final database admission boundary. [Cloud Run maximum instances](https://docs.cloud.google.com/run/docs/configuring/max-instances).

**Arithmetic verified locally:** `(6 + 2 + 1) * 3 + 4 + 2 = 33 <= 40`, leaving seven slots. The largest permissible integer pool is three; four would require 42. These are planned process/connection counts, not observed usage.

**Proposed enforcement:** one fenced active PgBouncer gateway, canonical database alias, API backend quota 27, workers four, maintenance two, reserve pools disabled and aggregate backend cap 33. Deny direct access and alternate aliases; bound queues and return retryable overload. Gateway failover must fence and drain the old gateway before replacement. PostgreSQL `max_connections=40` supplies a separate final server cap; reserved and provider connections must fit within it. Gateway/user limits are per gateway, so multiplying gateways is unsafe. [PgBouncer configuration](https://www.pgbouncer.org/config.html), [PostgreSQL connections](https://www.postgresql.org/docs/current/runtime-config-connection.html).

**State ownership:** only the primary-backed transaction service writes authoritative authorization and inventory. Workers call it; edge/KV has no independent write authority. Protected requests validate latest credential versions and lock current principal state in the same transaction as atomic conditional inventory updates and idempotency records. Revocation uses the same lock, drains preceding work and acknowledges after durable commit. Every later protected action checks the authority; no cached grants. Long-lived sessions and streams need per-action checks and explicit drain/cancellation tests. Authority failure denies protected operations. Origin authentication and application checks must prevent bypassing Cloudflare.

**Recovery proposal:** targets remain RTO 900 seconds and RPO 60 seconds; both measurements are null. Require synchronous durable acknowledgment for revocations and authoritative writes, backups/PITR, and a rehearsed runbook. Freeze writes; fence old primary and gateway; verify candidate replay position against acknowledged commit markers, replication lag and inventory/idempotency invariants. Retrieve and test the latest credentials/secret versions from independent secret management, including rotations after the backup; never trust restored old credentials. Promote one writable authority only after proving acknowledged revocations survive. Unknown lag, lost revocation evidence or uncertain fencing means stay closed, even if the RTO target is missed. Reopen after positive and negative authorization tests. A timed regional failure/restore drill must establish recovery time and actual lost commit interval before acceptance.

**Unverified acceptance work:** overload beyond nine processes; rollout/cold-start/termination overlap; connection high-water marks and pooler failover; direct origin/DB bypass; multi-location revocation races and partitions; concurrent last-item purchases, multi-row rollback, duplicate retries and commit crashes; latest-credential restoration, lag rejection, split-brain prevention and safe promotion. Confirm DB engine/version and hosting controls, existing sessions/reservations, synchronous-replication availability/latency, pooling compatibility, edge identity mechanism and stream semantics. PostgreSQL/PgBouncer are proposed implementation choices, not discovered infrastructure.
