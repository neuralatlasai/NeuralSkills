# D02-v2 decision

Reject the original KV-only authority and autoscaling-based connection guarantee. The replacement design is feasible in arithmetic and conditional on the acceptance tests in decision.json; it is not a deployed or verified system.

Use Cloudflare for edge delivery and Cloud Run for the regional API, with one transactional database authority for authorization and atomic inventory. Every protected path, including origin and workers, checks current authorization. Serialize revocation with protected transactions; acknowledge revocation only after earlier conflicting effects drain. Keep all multi-item inventory changes and idempotency records in one transaction. KV may cache display data, never grants or stock mutation authority. [Cloudflare KV documentation](https://developers.cloudflare.com/kv/concepts/how-kv-works/) documents eventual consistency, cached misses, and lack of suitable transaction semantics. [Durable Objects](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) offer strongly consistent transactional storage within an object; that alone supplies no cross-object transaction.

The fixed envelope is `(6+2+1)*3+4+2 = 33 <= 40`, leaving 7 sessions. Pool 4 would consume 42. The nine-process assumption sizes the plan; it is not the hard boundary. [Google Cloud](https://docs.cloud.google.com/run/docs/configuring/max-instances) states that maximum instances can briefly be exceeded. Proposed admission uses a single fenced active PgBouncer with database backend limit 40 and API/worker/maintenance user limits 34/4/2; all direct SQL access is denied. Confirm the actual version's options and their global scope before use. No independently budgeted active proxy replicas; failover fences and disconnects the former owner's sockets. Bound clients, queues and wait time, then reject excess work. `hardBoundary: true` describes this independent proposed design, not installed enforcement.

Before acceptance, run the burst/rollout/proxy-failover session count test, concurrent inventory/crash/retry tests, multi-location revocation and current-key tests, origin bypass denial, and isolated regional restore/failback. Recovery targets are 900 seconds RTO and 60 seconds RPO; both measured values remain null. Replication lag is an eligibility gate, not a guarantee: verify durable watermarks and acknowledged-write loss, fence the old writer, then promote. Recover the latest DB/signing credentials and revocation watermark from an independent failure domain. An RPO-compliant restore can still undo a recent revocation, so fail closed until reconciliation or invalidate old sessions and require fresh authentication. Measure useful secure service restoration, not merely resource creation. Unknown/excess lag or unproven fencing prevents promotion even if the RTO target is missed.
