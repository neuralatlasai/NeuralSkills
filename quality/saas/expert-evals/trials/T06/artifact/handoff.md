## Reproduced symptom and cause

Before repair, two Promise.all callers both selected the same pending row before the await, then both wrote token 1 and received apparently valid claims. After reclaim at injected now=10, the old owner completed at now=11, returned true, and stored STALE under the new owner's worker/token. See [original-failure.log](original-failure.log). This distinguishes missing atomic ownership checks from clock skew or delayed scheduling: all times were explicitly injected and the durable SQLite rows show duplicate token grants and the stale result overwrite. The original leaseMs=0 request was also accepted (returned null on a completed queue rather than rejecting).

The original causal interleaving is A reads pending token0; B reads pending token0; A writes workerA/token1; B writes workerB/token1; both return. Later C reclaims token2; A updates by id alone and changes C's result/status. The repair removes the unlocked read and applies completion ownership conditions in the same write statement as the result mutation.

## Why this mechanism

A BEGIN IMMEDIATE transaction enclosing SELECT plus UPDATE is a viable alternative. One UPDATE RETURNING fits this single-row invariant with fewer transaction/rollback paths and avoids an exposed intermediate selection. A transaction becomes appropriate when one lease grant must atomically reserve multiple rows or write related records. A broker, distributed lock service or outbox is unnecessary for this isolated local completion repair: none closes the original missing SQLite ownership predicate more directly, and each expands the authorized topology.

Claim becomes accepted at SQLite statement commit; returned claims are not kept in process memory. Completion and reclaim contend on the same SQLite writer boundary, so the winner is assessed against durable ownership at that boundary. A busy exception is distinct from null or false. No automatic retry hides contention. Reopen/process-exit tests establish persistence in this environment, not power-loss durability or full-disk recovery.

## Remote-effects boundary and remaining limits

A valid provider protocol uses a stable logical operation id (job identity plus queue incarnation), binds the payload parameters, and atomically records/deduplicates that id together with applying the remote effect and retaining its result. If ownership itself matters, the provider must atomically verify the current lease/epoch at its own effect boundary, or maintain an authoritative monotonic fence and reject older epochs; merely passing a local token is insufficient before the provider has learned the newer epoch. On lost acknowledgement, reconcile/retry the same provider operation id, reusing its recorded result rather than creating a new effect. Provider retention must exceed every allowed replay/recovery window. None of that provider path is implemented or exercised here.

Single-file SQLite serializes writes and depends on correct local file locking; it is not an independently available multi-host queue. Claim scans/sorts eligible jobs (worst-case O(N log N), payload/result storage and readJobs materialization also cost bytes); no capacity claim is made for large queues. readJobs intentionally preserves the fixture's unbounded inspection export. Worker code must use the trusted injected clock consistently; this adapter does not substitute wall time. Tokens persist for a row's lifetime and are exact only through 2^53-1; no delete/recreate or cross-database epoch protocol exists. Native busy waiting blocks that calling thread. Constructor failure cannot leave an acquired adapter connection; all acquired connections close in finally, including SQL errors. Connection cleanup is directly inspected and exercised on failure paths, not proven with a handle profiler.

The existing schema, exports, asynchronous claim return, claim object keys, null/boolean outcomes, payload and result storage remain compatible. Inputs that cannot represent a positive advancing lease now reject explicitly. No auth, UI, deployment, network or distributed guarantee was in scope. Coverage: API/data/async-local/verification changed; restart and SQLite arbitration inherited and verified; remote provider implementation and power-loss tests unperformed and not acceptance claims.
