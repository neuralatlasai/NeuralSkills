Run with Node 24.12+: `node service.mjs`. The process prints its loopback port; `DB_FILE` and `PORT` are optional. Run verification from this directory with `node verify.mjs`. It creates a new file-backed SQLite database under this artifact, uses actual loopback HTTP, closes/reopens the database, and writes verification.json. Original supplied files are in originals/.

PATCH /tickets/:id accepts a JSON object with a positive safe integer version and optional title/note. Title is trimmed and measured in JavaScript UTF-16 code units (1–120); note is unchanged text (0–500 code units) or null. Unknown fields fail. A version-only request succeeds and increments version. Tenant and write permission come only from the supplied identity registry. The public projection remains id,title,note,version. A single conditional UPDATE ... RETURNING performs the version comparison and mutation atomically; a failed match is distinguished as tenant-scoped 404 or stale-version 409. SQL values are bound parameters.

The parser buffers at most 2048 body bytes, rejects a larger declared Content-Length immediately, counts actual chunked bytes, and rejects invalid UTF-8/JSON. It returns JSON codes with the requested status. Headers timeout is 5 s, request timeout 10 s, socket inactivity timeout 15 s, and SQLite busy timeout 1 s. Node's timeout sweep scheduling means these settings are not hard real-time deadlines. The verification checks configuration; it does not run slow-client elapsed-time tests or capacity/load tests. SQLite calls are synchronous and this small service is a single process on loopback HTTP. No TLS, proxy, distributed consistency, backup, production identity, deployment, or external integration claim is made.

Observed runtime: Node v24.12.0, SQLite 3.50.4, Windows x64. node:sqlite emits its native ExperimentalWarning, preserved in verify.stderr.log. Correctness tests cover a pair of simultaneous HTTP requests at the same version in this runtime; they do not establish throughput or cross-machine guarantees.
