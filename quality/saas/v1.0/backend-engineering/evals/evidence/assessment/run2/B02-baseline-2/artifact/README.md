# B02 isolated repair

Run from this directory with Node 24.12+: `node verify.mjs`. Each run retains fresh file-backed databases under `verification-*` and writes `verification.json`. The unchanged supplied `probe.mjs` also runs against a fresh path: `node probe.mjs fresh-name.sqlite`.

The original implementation reproduced two 201 responses and two allocations against stock 5, quantity 4, version 1 (`before.stdout.json`). The repaired probe returns 201/409, stock 1/version 2 and one allocation (`after.stdout.json`). Seven checks passed in `verification.json` on Node v24.12.0, SQLite 3.50.4, Windows x64, SQLite DELETE journal mode, with 200 ms busy_timeout.

`reserve` keeps its exported asynchronous signature and both hooks. Input quantity must be a positive safe integer; tenant and item must be nonempty strings. Unknown scoped items return 404, stale versions or insufficient stock return 409. `afterRead` remains asynchronous and executes before taking a write lock. After that hook, BEGIN IMMEDIATE and a conditional UPDATE atomically recheck tenant/item/version/stock. Stock update, synchronous afterWrite hook and allocation insert share one transaction. A hook or insert/commit exception causes ROLLBACK and is rethrown. There is no await inside a held transaction and no application mutex.

Only SQLITE_BUSY at BEGIN is retried: three lock-acquisition attempts in total, 10 ms asynchronous gaps, SQLite busy_timeout 200 ms per attempt. Exhaustion returns 409 without a mutation. These are configured limits, not a latency guarantee: the measured exhaustion was about 936 ms on this machine. Commit-time busy or other database errors roll back and propagate. The fault hook is never automatically replayed. Actual lock contention produced ERR_SQLITE_ERROR / errcode 5 / database is locked. Tests cover retry after lock release, retry after a rolled-back injected fault, and retry after busy exhaustion.

Limits: afterWrite is a synchronous test hook with no external effects, as supplied; asynchronous or reentrant transactional hooks are unsupported. Callers must supply an open, transaction-idle connection and already trusted tenant identity. SQL tenant scoping is verified; authentication is outside this function. Direct SQL writers can bypass application validation because the inherited allocation table is unchanged. No idempotency key exists: retries after an ambiguous caller disconnect need a separate product contract. Process crashes, power loss, network filesystems, multiple OS processes, backup restoration, throughput and production deployment were not tested. SQLite's single-writer lock coordinates connections, but these local results do not establish universal durability or capacity guarantees. Native SQLite emitted its experimental-feature warning, retained in stderr logs.

Original fixtures and input/control copies are under `original/`. Both original and repaired probe stdout/stderr, verification stdout/stderr, real SQLite files, the failed patch attempt and command records are retained. `../result.json` separates responsibility dispositions from acceptance outcomes.
