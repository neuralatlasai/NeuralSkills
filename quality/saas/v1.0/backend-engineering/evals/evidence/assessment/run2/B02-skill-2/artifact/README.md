# B02 isolated reservation repair

Run from this directory with Node 24.12+:

```
node verify.mjs
node probe.mjs a-new-filename.sqlite
```

`original/` preserves the supplied store, probe, README, case and control. `store.mjs` keeps the existing exports and result shapes. `probe.mjs` is an unchanged copy. The original defect is retained in `logs/baseline.stdout.txt`: two 201 responses and two allocations for stock 5. The baseline probe itself exited 0 because it only prints state; this is a semantic failure, not a failed command. Raw verification stdout/stderr, command exit codes, intermediate runs and real SQLite files are retained. SQLite's experimental warning is preserved.

The caller still supplies tenant identity; no authentication system is provided by this direct module API. All reads and writes bind both tenant and item. Positive safe integer quantity is checked using the existing ordering: an absent item returns 404 before quantity validation; existing items with invalid quantity return 400. Mismatched versions or insufficient stock return 409. Existing allocation DDL is unchanged; guarantees cover this writer, not arbitrary direct SQL clients.

The asynchronous `afterRead` hook runs after the initial read and before opening a transaction. A conditional update rechecks tenant, item, expected version and sufficient stock inside `BEGIN IMMEDIATE`. The update, synchronous `afterWrite`, allocation insert and commit form one local SQLite transaction with no await inside it. The losing stale-version caller rolls back and returns 409. An injected hook or insertion fault rolls back and rejects with its original error. If rollback itself fails, an AggregateError requires discarding the connection. The synchronous hook must remain local, bounded and free of external effects; a local transaction cannot undo remote effects. Hooks must not manage transactions or reenter this connection. The caller owns the connection and must not already have a transaction open.

The tested environment was Node v24.12.0, SQLite 3.50.4, Windows x64. The inherited configuration is rollback journal `delete`, synchronous 2 (FULL), foreign keys on, and busy timeout 200 ms. SQLite permits one writer; DatabaseSync blocks the JavaScript thread during database calls and lock waits. The observed busy wait exceeded 200 ms under this host scheduling, so this pragma is not a hard end-to-end deadline. No mutex, connection pool, automatic retry or background work was added. A lock timeout is propagated as a SQLite error; the test records errcode 5 and explicitly retries the whole operation only after releasing the competing transaction. Hook exceptions and insertion failures are also retried explicitly only after confirmed rollback. No blind retries near an uncertain commit are claimed. Hook execution time itself is caller-controlled and unbounded.

Verification uses fresh, file-backed databases. Three forced races use two independent connections and a barrier that releases both callers after their reads. Each returns one 201 and one 409, with stock 1/version 2, one quantity-4 allocation, and unchanged south stock. The same connection probe is exercised too. Fault tests capture provisional state, rollback, file close/reopen and successful retry, including reuse of the original connection. Contract checks cover missing tenant/item, invalid quantity, insufficient quantity, stale/string version, exact depletion, SQL-looking tenant input, other tenant/item preservation and async read-hook failure. A real SQLite trigger also rejects allocation insertion to verify that the preceding decrement rolls back. This is cooperative asynchronous race testing on two connections in one process, not a multi-process stress test.

For N stock rows, lookups/conditional writes use the composite primary key; the retained query plan names the corresponding SQLite index. There are a fixed number of statements per reservation, with index access, payload binding and disk/journal work; this is not an O(1) end-to-end claim. One successful request adds one allocation, so retained allocation storage grows with accepted reservations A. The fixture has two stock rows (one additional row in the item-scope check), tiny string keys and at most two competing callers. Timing samples and their median/range are test diagnostics, not capacity or latency guarantees. No disk-full, power-loss durability, backup restore, distributed database, production auth, HTTP, deployment, capacity or unknown-commit outcome claims are made.

All L01-L24 dispositions and six requirement/decision mappings are in `../result.json`. The exact first tool invocation timestamp was not exposed or captured. Consequently startUtc and total elapsedSeconds are null; first recorded clock and elapsed lower bound are separately preserved rather than inventing a start time. Tool call count is manually enumerated and exact for this trial.
