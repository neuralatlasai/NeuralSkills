Requires Node 24.12+ native SQLite and built-ins only. Tested with Node v24.12.0 and SQLite 3.50.4 on Windows x64. From this directory:

```text
node verify.mjs
node worker.mjs jobs.sqlite --seed --crash-after-effect
node worker.mjs jobs.sqlite
node worker.mjs jobs.sqlite --seed
```

The intentional crash command exits 73. Run it on a fresh database to exercise the hook. The durable balance is already 7, the credit ledger has one row, and the job is still pending. Restart acknowledges the existing ledger without another balance update. Running `--seed` again replays acceptance. `verify.mjs` uses unique file-backed databases in `../evidence`, runs this real crash/restart three times, and writes raw child exit/stdout/stderr plus SQL observations to `../evidence/verification.json`. It also checks duplicates/conflicts, invalid enqueue, legacy poison jobs, normal completion, callback failure, transaction rollback, three-attempt exhaustion and subsequent healthy work. No process helpers remain after synchronous children exit; each child has a 10 second timeout.

The exported enqueue operation accepts `{id,account,amount}`. IDs must contain non-whitespace text and have at most 256 UTF-8 bytes; account names at most 128 bytes. Names and IDs retain their exact spelling. Amounts must be positive JavaScript safe integers. Accounts must already exist in `balances`; the fixture creates `north`. Enqueue uses a transaction, binds the ID durably, returns `{accepted:true,id}` for an identical replay and throws `JOB_CONFLICT` for different parameters. Invalid inputs throw `INVALID_JOB`. Retain jobs and ledger rows together indefinitely to retain replay protection; deleting identity records changes this guarantee.

`runOne` selects at most one pending job per invocation, ordered by ID using the `(state,id)` index. It records one durable attempt before a transaction that updates the balance and inserts a unique per-job credit ledger row. `afterEffect` runs after this transaction commits and before the separate acknowledgement. The actual CLI hook calls `process.exit(73)` at that point. A restart reconciles a matching ledger before considering retry exhaustion. Validation or unsafe-integer balance overflow produces terminal `failed`, never `done`. A storage error rolls back both local changes, preserves its error code and propagates to the caller; at most three effect attempts per job are permitted across invocations. There is no internal retry loop or sleep. After three storage failures the job is terminal failed. Operators must inspect failed jobs and explicitly repair them; enqueue does not reset their state or retry count. A post-effect callback error leaves a pending job with its committed ledger, so later acknowledgement remains safe.

The CLI closes the database on ordinary success/failure and returns exit 1 for thrown errors. Its diagnostic JSON limits each table to 100 rows and reports `snapshotLimit:100`; processing itself always consumes at most one job. SQLite busy waits are 250 ms per lock acquisition. This is a bounded amount of work per invocation, not a hard end-to-end wall-clock deadline or a bounded total queue. Enqueue/processing use a fixed number of parameterized statements with indexed identity/pending lookup, approximately O(log N + B) application/database lookup work for N retained jobs and B bounded payload bytes; disk scheduling, SQLite page/cache/locking work and fsync latency are additional engine costs. JavaScript materialization is one job or at most 100 rows per diagnostic table; retained storage grows O(N) and has no automatic cleanup. No throughput, memory ceiling, production latency or power-loss recovery result is claimed.

The guarantee covers one trusted local SQLite database, one active worker, and only a balance update and dedup ledger in that database. SQLite uses foreign keys, synchronous FULL and local transactions; process-crash testing is not power-loss, backup restore, disk-failure or distributed-systems verification. There is no broker, external credit effect, multi-worker lease, networking, authentication service or production deployment. Local atomicity does not establish distributed exactly-once delivery. The database file and direct SQL writers are a trusted boundary; production OS permissions are not established by this fixture.

Existing fixture schemas gain `attempts`, `error`, the credit ledger and an index. Legacy invalid pending jobs are rejected during processing. Already-applied effects from the original broken worker have no ledger and cannot safely be inferred or automatically repaired: reconcile such a database manually before using the repaired worker. Changing job payloads or deleting balances/ledger rows through direct SQL is outside the supported enqueue contract. A detected ledger/payload conflict remains pending and throws for manual reconciliation.
