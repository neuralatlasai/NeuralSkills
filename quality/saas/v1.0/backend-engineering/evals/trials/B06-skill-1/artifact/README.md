# Local carrier webhook

This is a runnable HTTP/1.1 + file-backed SQLite integration using Node v24.12.0 built-ins (SQLite 3.50.4 observed). Only POST /webhooks/carrier is supported. Run `node service.mjs` in this directory; DB_FILE selects a SQLite path, PORT defaults to an ephemeral loopback port. The CLI binds 127.0.0.1. The signing key is the supplied disposable fixture key, not a deployed secret.

The authenticated bytes are ASCII Unix-seconds timestamp + '.' + the exact incoming body bytes. Supply one x-carrier-time header and one 64-hex x-carrier-signature HMAC-SHA256 header. Timestamp skew is inclusive +/-300 seconds at completed body receipt; malformed or duplicate authentication headers fail. Every attempt, including a replay, must authenticate freshly. Re-sign an unchanged body with the current timestamp for delayed redelivery. Header timestamps are canonical unsigned decimal seconds, at most ten digits.

The body is a UTF-8 JSON object with exactly id, type and orderId. Both IDs are nonblank strings of at most 80 UTF-16 code units; type must be order.shipped. Unknown fields and types, arrays, null, malformed JSON and invalid UTF-8 fail. Standard JSON.parse semantics apply to duplicate JSON member names; the raw body still binds the signature and replay identity. No decompression is performed: non-identity content encoding fails. Content-Type, if supplied, must be application/json with optional UTF-8 charset.

The fixed signing identity authorizes tenant north only. An object lookup includes north; body/header tenant assertions grant no authority. The state transition is created to shipped. A new valid event for an already shipped north order records acceptance with no additional transition. No other CRUD operation is exposed.

BEGIN IMMEDIATE owns the receipt lookup, exact BLOB comparison, receipt insertion and conditional north-scoped state update. COMMIT completes before a 200 response. Receipt event_id is unique for this fixed integration identity; an identical body returns 200 with replay:true and causes no write. Reusing an event ID with different bytes, including different whitespace, returns 409. Unknown or unauthorized orders share 404. The beforeCommit hook is an in-process verification dependency, inaccessible over HTTP. A thrown hook rolls back both receipt and mutation.

Responses are bounded JSON with no stack, SQL, signed payload or secret. Success: 200 {accepted:true,replay:boolean}. Errors: 400 invalid, 401 signature (including stale/future timestamps), 404 not_found, 408 timeout, 409 event_conflict/state_conflict, 413 too_large, 415 unsupported_encoding/unsupported_media and 503 unavailable. Node's HTTP parser may reject malformed framing independently. All application responses use no-store and close their connection. The supplied carrier retries non-2xx; clients should fix permanent 4xx errors and quarantine conflicting IDs instead of blindly looping. For transient 408/503 or lost acknowledgements, retry the exact same event bytes and identity with a fresh signature; use a bounded caller retry budget (suggested maximum three attempts within a total 30 seconds with jitter). This service makes zero outbound requests and has no internal retry loop. If the connection disappears near commit, the caller's outcome is unknown until an authenticated identical replay reconciles the receipt; a failed response alone is not proof of rollback.

Application body buffers admit at most 8192 bytes per request and 16 concurrent active requests; excess active requests return 503. Content-Length and streaming chunks are both checked. A 5-second application body timer rejects incomplete bodies; there is no application work queue. maxConnections=32, maxHeadersCount=32, HTTP header limit8192 bytes, header timeout5 seconds, request timeout6 seconds and keepalive timeout1 second. Transport/kernel/runtime overhead lies outside the body-buffer bound. Parsing/hashing/comparing are O(B), B<=8192, and each admitted request holds O(B) application bytes, plus a Buffer.concat and UTF-8/JSON copies. SQL access uses primary-key indexes, with approximately O(log N) index lookup/update work and lock/I/O costs that depend on storage. SQLite synchronous operations and its 1-second busy timeout can stall this process's event loop; this is a small local integration, not a production latency or throughput claim.

Receipts are retained indefinitely until explicit database deletion. No automatic pruning or expiry is implemented; exact-byte redelivery protection lasts while the receipt remains. Storage grows O(E*B) for E distinct accepted events, plus database/index overhead. Disk exhaustion is handled as unavailable where SQLite reports failure; disk quota/monitoring and retention migration are operational work, not verified here. Do not delete receipts while provider redelivery remains possible. SQLite file/OS access is the privileged trust boundary; there is no SQL GRANT/RLS. Only process restart recovery was tested: no backup restore, power-loss, multi-host availability, secret rotation or production TLS claim is made. Loopback cleartext is this synthetic local boundary. Existing deployed database migration compatibility is not established.

MCP support: UNSUPPORTED. No MCP server, SDK, negotiated protocol revision, discovery/schema adapter, MCP transport/session lifecycle, tool authorization, cancellation, output validation or adapter tests are present. These operations could be wrapped by a separately designed and verified MCP runtime in future, while preserving tenant authority and durable event identity. HTTP request IDs must remain distinct from event IDs. This artifact neither implements an MCP server nor claims MCP or SDK conformance. No live carrier was contacted and no package was downloaded.
