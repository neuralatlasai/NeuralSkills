# API, parsing and domain execution — B3

Activate for L06–L08. Inputs are callers/authority, resource/schema versions, invariants, workload, data/side-effect owners and actual media/protocol support. Depend on B1 and B2 policy; coordinate B4/B5 at transaction and durable-acceptance boundaries. Output an operation contract and working route→domain→storage path. Select limits from the task before running tests.

For inventory-like invariants, validate positive quantity and trusted tenant, then perform an atomic conditional update such as `SET available = available - ?, version = version + 1 WHERE tenant_id = ? AND item_id = ? AND version = ? AND available >= ?`. Interpret zero rows according to the denial/absence/stale/stock contract without leaking unauthorized existence. Multi-row invariants require separate constraint/isolation/locking analysis. An unconditional write after an application check remains racy.

Idempotency is a logical-effect contract, not a requirement that HTTP response codes always match. A particular API may promise stored response replay; state its exact headers/body/status policy. Check key+parameters and effect in a shared atomicity boundary; external effects may require outbox/inbox, provider idempotency or explicit unknown-outcome reconciliation. Do not treat an in-memory key map as durable protection across restart or multiple replicas. Retention must cover real client/job replay horizons, and every attempt must still satisfy current authorization.

Failure handling: rollback the whole invalid local operation; retry complete safe transactions only for classified transient outcomes with a bounded budget. Preserve ambiguous commit/external results and use logical-operation reconciliation. A mocked repository proves only the mock's behavior.
