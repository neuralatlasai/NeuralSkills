# IEEE-related engineering and coding note

This note makes the package's existing evidence rules explicit. It is not a certificate or a new universal code-format rule. The applicable public reference baseline is ISO/IEC/IEEE29148:2018 for sourced verifiable requirements and ISO/IEC/IEEE42010:2022 for architecture descriptions; use ISO/IEC25010:2023 to select quality objectives. Full normative ISO texts were not accessed. A clause-level or formal conformance claim requires the actual applicable text, scope and assessment.

For each consequential change retain `requirement ID → source → decision/mechanism → affected artifact → operating limit/failure → verification/result`. Describe the relevant stakeholder concerns, state/authority owners, interfaces, deployment boundaries and relationships proportionately. Keep one current definition and reconcile dependent code/tests when it changes. Test results, estimates, assumptions and unperformed checks remain distinct. No test count or self-rating establishes engineering quality.

Concrete coding checks follow the real project: inspect scripts/lockfile first; preserve supported versions/conventions; use explicit typed contracts where the stack supports them; validate untrusted data at runtime; keep side effects and state ownership clear; bound resources and failures; use meaningful static/build/runtime/integration checks; review changes and retain failures. Run lint/format checks when the project config actually supplies them. Do not invent a linter result or add arbitrary formatting infrastructure merely to use the word IEEE.

For frontend, additionally verify semantic controls, keyboard/focus, responsive states/content, reference fidelity and applicable accessibility/performance categories. WCAG is the web accessibility reference, not an IEEE certification. For backend, additionally verify trusted identity/tenant/field policy, atomic invariants/real database paths, ambiguous effects, admission/retry/deadline limits, recovery and telemetry. Type checking alone does not prove either boundary.

The authoring report links actual compiler, runtime, browser, database, fault and resource evidence and lists missing coverage. JavaScript that only receives syntax/integration checks must not be described as fully statically typechecked. Successful local checks do not establish inaccessible standards clauses, production guarantees or unsupported platforms.
