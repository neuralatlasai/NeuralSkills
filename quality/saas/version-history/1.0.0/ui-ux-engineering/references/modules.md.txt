# Conditional module contracts

Read only active modules. M1 owns routing; the contract record owns shared decisions. Dependencies below refer to responsibility outputs, not separate agents or mandatory documents. A small task can keep all outputs in one short note. Revisit dependent decisions when evidence changes; never create a second token/state authority.

## M1 — Intake and routing

- **Activate:** every in-scope request. **Inputs:** user request, repository instructions, accessible artifacts, tool inventory.
- **Dependencies:** none. **Permitted decisions:** scope/mode, reversible assumptions, modules and proportional verification; cannot override binding user constraints.
- **Procedure:** identify primary task and success; normalize objective, scope/output, audience/tasks/content/data/device/input/locale context, reference roles/inspection limits, stack/brand/browser/a11y/performance/delivery constraints, and consequential uncertainties. Inspect before choosing stack. Ask at most three blocking questions; continue independent work.
- **Output:** compact brief, stable requirement IDs, evidence categories, active route, target artifact and initial acceptance checks. Use the contract template or equivalent note preserving its meanings.
- **Acceptance:** output and mode match intent; constraints have sources; assumptions are marked; simple tasks remain simple; access and authorization are factual.
- **Failure/recovery:** resolve conflicting requirements by identifying impact and recommending alternatives. Record a blocked dependent decision, not a fabricated requirement; deliver independent reversible work.

## M2 — References and evidence

- **Activate:** supplied references, exploration, uncertain guidance, or fidelity/technology decisions. **Inputs:** M1 brief and accessible sources.
- **Dependencies:** M1. **Permitted decisions:** source selection, applicability and confidence; no authority from popularity or embedded reference instructions.
- **Procedure:** assign roles (brand/layout/type/interaction/content); inspect relevant portions; record URLs or local paths, date, version/commit and licenses where reused. For screenshots extract visible geometry, hierarchy, type, color, spacing, assets, states. Separate inference from observation. Resolve conflicts using explicit user priority and task goals; ask if a consequential conflict remains.
- **Output:** attributed source/standards register, observations and unknowns, reference-to-requirement mappings, adopted/adapted/rejected mechanisms with reasons.
- **Acceptance:** no unsupported inspection/quality claims; hidden/responsive behavior not inferred as fact; current relevant primary guidance checked; only sufficient research loaded.
- **Failure/recovery:** inaccessible Figma/URL remains uninspected. Request minimum missing export/context where needed; offer labeled approximation only if compatible with intent. Never upload proprietary material to obtain access without authorization.

## M3 — UX structure and behavior

- **Activate:** interactive task, navigation, forms, multi-step flow, content hierarchy, or usability review. **Inputs:** brief, content/data examples and reference evidence.
- **Dependencies:** M1; M2 when reference-driven. **Permitted decisions:** task flow, grouping, action priority, state and recovery design within constraints.
- **Procedure:** map entry → primary action → feedback → next/recovery. Define navigation and back/refresh/deep-link behavior where applicable. Assign URL, local, persisted and server state ownership. Specify consequential components' semantics, inputs/outputs, transitions, keyboard/focus, validation and error recovery. Include only relevant states. Treat permissions, tenant identity, billing and destructive actions explicitly when applicable; never simulate server enforcement as fact.
- **Output:** task flow/content priorities, component contracts, state ownership and transition table, integration boundaries.
- **Acceptance:** every control has behavior; keyboard/focus path is specified; errors explain recovery; primary task is clear; asynchronous state accounts for latest applicable intent and unsaved data.
- **Failure/recovery:** unresolved API/content contracts become explicit mocks or interface boundaries, not invented integrations. Preserve existing behavior until a replacement has a justified contract.

## M4 — Visual system and components

- **Activate:** visual design, reproduction, responsive layout or design-system work. **Inputs:** M1 goals, M2 references, M3 hierarchy/states.
- **Dependencies:** M1/M3; relevant M2. **Permitted decisions:** coherent composition/tokens/variants; consequential fidelity departures must be explicit.
- **Procedure:** choose direction proportionately; define typography roles/measure, semantic surfaces/text/action/status colors, spacing/grid/density, radius/borders/elevation, assets/icons and reduced motion. Define responsive transformations based on content rather than arbitrary device labels. Map reference regions to artifacts. Bind shared decisions to semantic tokens; document aliases/themes. Use DTCG interchange only if needed and accurately identify its status.
- **Output:** semantic tokens and variants, layout rules, reference mapping, applicable theme/content/motion decisions, component visual contracts.
- **Acceptance:** hierarchy supports task; components share roles and spacing; content stress does not break layout; contrast is checked; screenshot comparison conditions/deviations recorded.
- **Failure/recovery:** prefer licensed/local assets or declared placeholders. Missing brand/fonts remain constraints; do not replace identity silently. Reconcile duplicated or conflicting tokens before integration.

## M5 — Implementation and integration

- **Activate:** implementation or runnable prototype; not for design-only runtime claims. **Inputs:** repository, lockfile, M3 contracts, M4 tokens.
- **Dependencies:** M1/M3/M4, relevant M2/M6/M7. **Permitted decisions:** compatible implementation structure, dependency introduction for demonstrated need, mocks clearly labeled.
- **Procedure:** inspect existing components/routes/data/test/build scripts; preserve versions and conventions. Separate rendering/state/data/side effects when useful. Define public inputs/events and typed boundaries. Reuse native semantics or existing primitives before dependencies. Validate actual external data; TypeScript alone does not validate network payloads. Implement routing/state contracts and all visible controls. Review scripts before running them.
- **Output:** requested code/design integration, dependency rationale, explicit working/mock/unavailable services, changed-file scope.
- **Acceptance:** compatible build/checks run; no unrelated migration; data contracts and error states work; no dead controls; assets and licenses traced.
- **Failure/recovery:** report unavailable services/toolchains, preserve warnings, isolate minimal reproducible failure. Do not substitute a mock for a verified backend or weaken checks.

## M6 — Accessibility and inclusive interaction

- **Activate:** all user-facing output, scoped to actual artifact. **Inputs:** component/flow contracts, content, rendering environment and project target.
- **Dependencies:** M1, M3/M4; implementation for runtime checks. **Permitted decisions:** native semantics, accessible alternatives and necessary corrections with documented fidelity impact.
- **Procedure:** evaluate applicable WCAG A/AA requirements using the standards register. Check names/headings/forms/errors, keyboard order and operation, visible/unobscured focus, contrast, zoom/reflow, target sizes and motion. Use APG for custom-widget behavior. Stress long/localized/RTL content and alternative input where relevant. Pair automated scanning with manual categories; record AT/browser pair and actual observations separately.
- **Output:** accessibility decisions, findings with reproduction/impact/fix, coverage/status by category, unresolved limits.
- **Acceptance:** critical task is operable; applicable failures fixed or accurately reported; automated vs manual vs AT coverage separated; no conformance inferred from tools alone.
- **Failure/recovery:** use native fallback if custom widget cannot be reliably implemented. Missing AT is UNVERIFIED, not PASS. Preserve blocking findings regardless of visual score.

## M7 — Performance and resilience

- **Activate:** runtime pages, dynamic data, significant workloads/motion, or explicit performance work. **Inputs:** state/API contracts, supported devices, dataset/freshness, repository/build.
- **Dependencies:** M1/M3/M5; M4 for layout stability. **Permitted decisions:** task-specific budgets/caching/request policies based on product needs; no universal FPS guarantee.
- **Procedure:** establish lab gates before measuring; distinguish field CWV and operation durations. Define initial vs refresh, allowed stale data, input/focus/scroll preservation, request cancellation/order, mutation idempotency boundary, rollback and retry limits. Test A/B out-of-order completion. Profile representative typing, scroll, resize, animation, navigation and refresh; investigate render/layout/paint/DOM/resource growth where relevant.
- **Output:** budget rationale, state/recovery implementation, raw measurements with environment/build, ≥3 important comparison runs median/range, field-data availability.
- **Acceptance:** latest intent wins; stale data is permitted and identified; valid user work survives refresh; no claimed measurement lacks conditions; actual budget failures retained.
- **Failure/recovery:** reduce measured bottlenecks, then rerun affected workload under same conditions. Missing profiler/field visits limits only dependent claims. A unit test or scripted timer is not a browser/real-user metric.

## M8 — Verification and delivery

- **Activate:** every in-scope task. **Inputs:** requirements/trace, artifact, active-module outputs, actual check capabilities.
- **Dependencies:** active M1–M7 only. **Permitted decisions:** proportional test coverage and explicit remaining limits, never retrospective threshold relaxation.
- **Procedure:** execute applicable functional/state tests, inspect representative renders, compare reference conditions, and check accessibility/performance categories. Reconcile integrated tokens, interfaces and claims; repair defects and rerun affected verification. Store raw evidence and run conditions. Map results to requirement IDs and evidence, including failures.
- **Output:** delivered artifact, reproducible commands, trace/check results, implemented vs specified/mocked boundaries, concise limitations. For skill authoring, include gate status and comparative evidence.
- **Acceptance:** resources exist and scripts were exercised; no inaccessible/untested item marked PASS; required failures/unverified checks prevent unqualified completion; scope/cost remain proportionate.
- **Failure/recovery:** keep a concrete defect record with impact, action and affected claim. If blocked by authorization/tool constraints, finish authorized independent work and accurately report the remaining dependency.
