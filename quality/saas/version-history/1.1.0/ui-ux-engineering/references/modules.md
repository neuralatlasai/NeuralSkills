# Conditional module contracts

M1 selects active responsibilities; the shared contract owns current decisions. Dependencies are outputs, not mandatory agents/documents. Small requests can keep outputs in a short note. Read only active procedures; one coordinator reconciles parallel work.

## M1 - Intake and routing

- **Activate:** every in-scope task. **Inputs:** request, repository guidance, artifacts and actual tools.
- **Dependencies:** none. **Permitted decisions:** mode, scope, reversible assumptions and proportional checks within binding constraints.
- **Procedure:** inspect context/versions; identify primary task, output, reference roles, constraints, uncertainty and acceptance.
- **Output:** compact sourced brief, requirement IDs, active route and checks.
- **Acceptance:** intent/constraints preserved; evidence categories distinct; simple tasks stay simple.
- **Failure/recovery:** ask at most three consequential questions; explain conflict/consequence/alternative and continue independent work.

## M2 - References and evidence

- **Activate:** reference/fidelity/exploration or consequential evidence gap. **Inputs:** M1 brief and accessible sources.
- **Dependencies:** M1. **Permitted decisions:** relevance, applicability and confidence, never authority from popularity.
- **Procedure:** assign source roles; inspect relevant portions; record provenance/version/license; separate observation from inference.
- **Output:** attributed decision basis, mappings, adopted/rejected mechanisms and unknowns.
- **Acceptance:** inspected scope truthful; hidden screenshot behavior not invented; research resolves a named need.
- **Failure/recovery:** inaccessible material remains uninspected; request minimum missing evidence or label an authorized approximation.

## M3 - UX structure and behavior

- **Activate:** task flow, controls, navigation or hierarchy. **Inputs:** brief, realistic content/data, reference evidence.
- **Dependencies:** M1 and relevant M2. **Permitted decisions:** task grouping, action priority and transitions within constraints.
- **Procedure:** map entry/action/feedback/recovery; assign URL/local/persisted/server ownership; define component, keyboard/focus and recovery contracts.
- **Output:** flow/content priorities, state authority and legal transitions.
- **Acceptance:** every control works/is specified; errors recover; valid work and latest applicable intent follow policy.
- **Failure/recovery:** unknown APIs become explicit boundaries/mocks; preserve behavior until replacement is justified.

## M4 - Visual system and components

- **Activate:** composition, reproduction, responsive layout or system work. **Inputs:** hierarchy, references and content stress.
- **Dependencies:** M1/M3 and relevant M2. **Permitted decisions:** direction, semantic roles and variants; disclose fidelity deviations.
- **Procedure:** preserve established direction; compare alternatives for exploration/consequential uncertainty. Define visual/responsive roles; map reference to artifact and tokens to consumers.
- **Output:** coherent visual/component contracts and chosen tradeoffs.
- **Acceptance:** hierarchy serves task; state/theme/content consumers remain consistent, readable and usable.
- **Failure/recovery:** missing assets stay constraints; reconcile conflicting tokens and consumer impact before integration.

## M5 - Implementation and integration

- **Activate:** code or runnable prototype. **Inputs:** actual repo/lockfile, component/state/token contracts.
- **Dependencies:** M1/M3/M4 and relevant M6/M7. **Permitted decisions:** compatible structure/dependencies for demonstrated need.
- **Procedure:** trace affected path; implement semantics, typed/runtime boundaries, side effects and eligible completions; reuse conventions/primitives.
- **Output:** working artifact, changed scope, data interfaces and real/mock/unavailable boundaries.
- **Acceptance:** relevant build/runtime/integration checks, no dead controls or unrelated migration.
- **Failure/recovery:** isolate failures; preserve warnings; do not substitute mocks for verified services or weaken checks.

## M6 - Accessibility and inclusion

- **Activate:** user-facing artifact. **Inputs:** content, behavior, rendering environment and applicable target.
- **Dependencies:** M1/M3/M4; implementation for runtime claims. **Permitted decisions:** native semantics and documented necessary corrections.
- **Procedure:** verify relevant names/structure/forms, keyboard/focus, contrast, zoom/reflow, targets/motion and locale/input; separate automation/manual/AT.
- **Output:** scoped decisions/findings, actual coverage and unresolved limits.
- **Acceptance:** implemented task operable, design-only behavior specified; findings independent of visual preference; no conformance inference from automation.
- **Failure/recovery:** use a suitable native fallback when custom behavior cannot be reliable; missing tests remain UNVERIFIED.

## M7 - Performance and resilience

- **Activate:** runtime delivery, dynamic data, costly workload/motion or performance task. **Inputs:** device/data/freshness and state/API contracts.
- **Dependencies:** M1/M3/M5 and relevant M4. **Permitted decisions:** justified budgets, requests/caching and bounded recovery.
- **Procedure:** establish applicable runtime budgets/resilience checks; guard data scope/intent and reconcile valid work. Profile/compare for a performance task, observed problem or optimization change.
- **Output:** policies/conditions, field availability and, when measuring, raw comparison runs/median/range.
- **Acceptance:** valid work survives as permitted, revoked/stale outcomes cannot restore invalid state, claims match measurement.
- **Failure/recovery:** retain failed hypotheses/budgets; repair and rerun affected workload under comparable conditions.

## M8 - Verification and delivery

- **Activate:** every in-scope task. **Inputs:** trace, artifact, active outputs and actual checking tools.
- **Dependencies:** active M1-M7 only. **Permitted decisions:** proportional evidence coverage, never retrospective threshold relaxation.
- **Procedure:** execute applicable tasks/states, inspect renders/reference/a11y/performance, reconcile integration, repair/retest and retain raw evidence.
- **Output:** artifact, reproducible checks, requirement results and explicit support limits.
- **Acceptance:** resources/scripts usable and exercised; required failures/unknowns prevent unqualified completion.
- **Failure/recovery:** record defect/impact/correction; finish authorized independent work and disclose the concrete blocker.
